## Research Brief

**Question:** What is the current (2025-2026) state-of-the-art stack and architecture for a living, persistent 3D office interior in Three.js — driven by an external agent process — that runs several animated AI-agent characters through standup/desk/conversation behavior at 60fps in a browser?

**Opinion:** Build on raw **three.js r17x** (not r3f) for the character/simulation layer, with **glTF kit-bashing** (Quaternius/Kenney-style low-poly office packs, hand-placed, not procedurally generated) for the interior, **baked lightmaps** for static architecture plus a handful of realtime lights for characters, **navcat** for navigation (not recast-navigation-js or three-pathfinding), and a **fixed-timestep server tick + client-side interpolation buffer** for the external-drive layer. Cap the character budget at roughly **30-60 fully-skinned, individually-animated agents** before an office scene needs LOD/instancing tricks — an office with "several" agents (per the brief: standup + desks, plausibly 5-20) is comfortably inside the naive-SkinnedMesh budget and does not need instanced-skinned-mesh hacks. r3f is a legitimate alternative only if the driving application is otherwise a React app; it buys nothing for the simulation/navigation logic itself.

**Confidence:** Medium overall — High on performance envelope and navmesh library choice (direct primary-source evidence), Medium on framework layer and lighting (good secondary sources, some marketing-flavored), Low/Speculative on the external-drive-pattern facet (corpus does not cover it directly; reasoned from adjacent primary-source evidence in the crowd-simulation APIs instead).

**Reasoning:**
Hypothesis going in: r3f + recast-navigation-js + procedural generation + instancing would be the "modern" answer. The corpus overturned two of these. First, on navigation: `recast-navigation-js`'s own README (06-github-com-isaac-mason-recast-navigation-js.md) points readers to **navcat** as its recommended successor — "this library will continue to be maintained... [but] consider giving [navcat] a try" — because navcat is pure JS (no ~40ms WASM init cost), engine-agnostic, and ships the same algorithms plus a batteries-included `crowd` API with agent-to-agent avoidance and frame-distributed pathfinding (04-github-com-isaac-mason-navcat.md). `three-pathfinding` (05-github-com-donmccurdy-three-pathfinding.md) is querying-only — it doesn't generate navmeshes and is effectively legacy (2017, last real feature work old) — you'd still need navcat/recast/Blender to build the mesh. Second, on procedural generation: the one real example found (09-cryingcrocgames-itch-io-procedurally-generated-rooms.md) is a student capstone project explicitly warned as "resource intensive" and "unstable" — not evidence of a production-shipping pattern. Nothing in the corpus shows procedural generation shipping for a hand-crafted-feeling office; kit-bashed/hand-placed glTF is the default assumption underlying every lightmap-baking workflow found (07, 08), which all presume a fixed, hand-authored scene (baked lighting requires static geometry — "no object can move because the shadow it casts is baked into textures of surrounding objects," 07-tchayen-github-io-posts-baked-lighting-in-r3f.md).

On performance, the hypothesis "instancing is mandatory for animated crowds" also did not survive contact with primary evidence. The most valuable single source in the corpus (11-discourse-threejs-org-t-optimization-of-large-amounts-100-10.md) is a first-hand case study: a developer profiling **300 individually-animated SkinnedMeshes** (700 tris, 25 bones, 128×128 textures each) on a 2014-era laptop CPU hits the frame-budget wall **between 200-300 units**, and the bottleneck is CPU-side (`AnimationMixer.update`, `updateMatrixWorld` on bone hierarchies, `Skeleton.update`) — not GPU draw calls, so `InstancedMesh` doesn't fix it for animated characters the way it fixes it for static props (12, 14). A second discourse thread (13) confirms animated-instanced-skinned-mesh is still a hand-rolled, unmerged, addon-only technique in 2022-2026, gated behind bone-texture-atlas hacks and per-instance LOD — real but non-trivial engineering, only worth paying for above roughly 200+ simultaneous animated characters. An office standup scene with "several" agents (5-20 is the realistic reading of the brief) sits an order of magnitude below that cliff — naive per-agent `SkinnedMesh` + `AnimationMixer` is the correct, boring answer, and instancing effort should be reserved for background dressing (chairs, monitors, plants — see 12, 14 on `InstancedMesh`/`BatchedMesh` for static repeated geometry) not for the characters.

On the framework layer, the corpus supports "R3F is the right choice conditional on the host app already being React, not an independent argument for or against it here" — three independent 2026 comparison pieces (01, 02, 03) converge: R3F adds no runtime overhead ("Components render outside of React... It outperforms Threejs in scale due to React's scheduling," 01-github-com-pmndrs-react-three-fiber.md) and its ecosystem (drei, rapier, postprocessing) genuinely speeds iteration, but the underlying simulation/networking/navmesh code is identical either way — r3f wraps the render layer, not the agent-behavior layer. Given the driving requirement here is a server pushing discrete events into a simulation loop (not a React-state-driven UI), raw three.js keeps the render loop and the WebSocket event-consumer in the same idiom without a reconciler in between; r3f is the pick only if the surrounding app (a dashboard, a control panel) is already React and the office scene is embedded as a component.

On the external-drive facet, the corpus has no direct source — no page discusses WebSocket/SSE-driven three.js scenes. The strongest adjacent primary-source evidence is `recast-navigation-js`'s own `Crowd.update` API (06-github-com-isaac-mason-recast-navigation-js.md), which documents exactly the pattern this brief needs one layer down: "fixed time stepping with interpolation... will update the `interpolatedPosition` vector3 on each agent, which you can use to render a smoothly interpolated agent position between updates" — i.e., decouple the authoritative low-frequency tick (here: server events) from the 60fps render loop via an interpolation buffer, the same technique client-side prediction/interpolation uses in networked games generally. This is reasoned by analogy, not corpus-sourced for the specific websocket/SSE case — flagged as the weakest-evidenced facet in this brief.

**Key evidence:**
- recast-navigation-js README recommends navcat as its own successor, pure JS, no WASM init cost — supports — `pages/06-github-com-isaac-mason-recast-navigation-js.md`, `pages/04-github-com-isaac-mason-navcat.md`
- three-pathfinding is query-only, cannot generate navmeshes, external tool required (Blender/Recast/navcat) — supports (navcat over three-pathfinding) — `pages/05-github-com-donmccurdy-three-pathfinding.md`
- navcat's `crowd` API ships agent-to-agent + wall avoidance, frame-distributed pathfinding out of the box — matches the "standup circle + desk dispersal" use case directly — `pages/04-github-com-isaac-mason-navcat.md`
- 300 individually-animated SkinnedMeshes hit a CPU (not GPU) wall between 200-300 units on a weak laptop; root cause is AnimationMixer/bone-matrix math, not draw calls — supports the "instancing doesn't help animated crowds until you're past ~200" position — `pages/11-discourse-threejs-org-t-optimization-of-large-amounts-100-10.md`
- Animated instanced skinned mesh remains an unmerged, hand-rolled addon technique (bone-texture atlases, per-LOD mixers) as of the most recent thread activity — challenges "just use InstancedMesh for characters" as a naive first move — `pages/13-discourse-threejs-org-t-animated-instanced-skinned-meshes-gl.md`
- Baked lighting requires fully static geometry ("no object can move") — challenges pairing baked lightmaps with anything except the architectural shell; characters/movable props need realtime lights layered on top — `pages/07-tchayen-github-io-posts-baked-lighting-in-r3f.md`
- The one procedural-room-generation example found is a student project flagged by its own author as resource-intensive and unstable in Chrome — challenges "procedural generation ships for office interiors" — `pages/09-cryingcrocgames-itch-io-procedurally-generated-rooms.md`
- R3F "outperforms Threejs in scale due to React's scheduling," no overhead, full API parity — supports r3f as viable, not superior, for this use case — `pages/01-github-com-pmndrs-react-three-fiber.md`
- recast-navigation-js Crowd API's fixed-timestep + `interpolatedPosition` pattern — analogy-supports the external-drive interpolation-buffer recommendation — `pages/06-github-com-isaac-mason-recast-navigation-js.md`
- InstancedMesh/BatchedMesh are the correct tool for *static* repeated props (desks, chairs, monitors), 10x+ FPS gains documented — supports using instancing for set-dressing, not characters — `pages/12-waelyasmina-net-articles-instanced-rendering-in-three-js.md`, `pages/14-www-intelligentgraphicandcode-com-development-threejs-interf.md`

**Conflicts / unknowns:**
- Two of the three framework-comparison articles (02, 03) read as SEO/marketing-adjacent content (npm-download-stat pieces, "Top 5 trends" listicles) rather than primary engineering sources; their specific 2026 claims (e.g., R3F WebGPU maturity timeline, "react-three-ai" natural-language scene generation) are treated as directional color, not load-bearing evidence. Where they agree with the primary source (01, the r3f repo itself), that agreement is the load-bearing claim.
- The performance-cliff number (200-300 animated SkinnedMeshes) comes from a single detailed forum post on old hardware (i7-4720HQ, 2014 laptop) — a strong primary source in kind (first-hand profiling with numbers) but a sample size of one machine; treat "200-300" as the floor for weak hardware, not a hard ceiling on modern hardware.
- The websocket/SSE external-drive pattern has no direct corpus source at all (see Corpus limits) — the recommendation for a fixed-tick-plus-interpolation-buffer architecture is inference from an adjacent (crowd-simulation) primary source, not a directly-cited websocket-pattern source.

**Would change this opinion:** A primary source showing procedural office-layout generation shipping in a production (non-student, non-demo) product would weaken the kit-bashing recommendation. A newer (2026) first-hand profiling post showing animated-crowd CPU limits above ~500 on typical modern hardware would raise the "when to bother with instancing" threshold and further reinforce not instancing for a small office cast. A dedicated primary source on websocket-driven three.js scene reconciliation would either confirm or overturn the interpolation-buffer recommendation, which is currently the weakest-evidenced part of this brief.
